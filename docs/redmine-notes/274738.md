## 1. 판정

**8kHz 전화·상담 음성에서, 클라이언트 로컬 단독(브라우저 내 Whisper WASM)으로 "읽히는 실시간 자막"을 만드는 것은 현재 실측으로 불가하다. 단 실패의 원인은 안정성이 아니라 정확도이며, 정확도 요구를 낮춘 용도(사후 기록·색인)에서는 로컬 단독으로도 도달 가능하다.**

판정을 가른 사실은 세 가지다.

**(1) 타이밍과 유실은 이미 요건을 충족한다.** 브라우저 로컬의 확정 결과는 발화가 끝난 뒤 **약 1.3초**에 도착한다. 이는 온프레미스 서버(약 1.4초)와 같은 수준이다. 확정 유실(인식 결과가 한 건도 오지 않는 실패)은 브라우저 로컬 경로에서 **측정 94회·발화 관측 597건 중 0건**으로, 세 실행 위치 중 가장 안정적이다.

**(2) 판정을 가른 것은 정확도이고, 그것도 평균이 아니라 실패의 분포다.** 브라우저 로컬은 문자 오류율(CER) 평균이 문제가 아니라 **발화 관측의 22~28%가 CER 50% 이상으로 무너진다.** 온프레미스 SenseVoice와 클라우드는 같은 발화 집합에서 CER 50% 이상이 **0%**다.

**(3) 그 실패는 노이즈가 아니라 재현된다.** 무너지는 두 발화(`S1`·`S4`)는 반복 측정 6회 전부에서 CER 42% 이상이다. 같은 발화를 클라우드는 10~11%, 온프레미스 SenseVoice는 14~16%로 처리한다 — **발화 자체의 난이도나 정답 전사 품질 문제가 아니라 브라우저 로컬 경로 고유의 결함이다.**

| 실행 위치 | 구성 | 문자 오류율(micro) | 발화 CER≥50% 비율 | 확정 지연(중앙) | 확정 유실 |
|---|---|---|---|---|---|

### 그래서 무엇이 가능한가

- **실시간 자막(사람이 화면에서 읽는다)** — 클라이언트 로컬 단독으로 **불가**. 정확도를 올리려 모델을 small로 키우면 짧은 발화도 확정이 **13초 뒤**에 오고, 35초 연속 오디오는 처리에 84초가 걸려(**오디오 길이의 2.4배**) 실시간 경로에서 배제된다(§4.5).
- **사후 기록·검색(나중에 읽거나 텍스트로 찾는다)** — 클라이언트 로컬 단독으로 **조건부 가능**. 실시간을 포기하고 파일 전체를 한 번에 인식하는 배치 경로는 같은 데이터셋에서 CER 23.4%(긴 오디오)/24.6%(짧은 발화)까지 내려간다.
- **키워드 추출·색인** — **판정 보류**. 키워드 재현율을 측정한 기록이 없다(§5).

### 온프레미스·클라우드를 "더 안전한 기본값"으로 볼 수 있는가 — 근거 없음

정확도 순위는 클라우드 > 온프레미스 > 클라이언트 로컬로 확실하지만, 그것이 곧 서비스 기본값의 근거가 되지는 않는다.

- **온프레미스**는 추론 스레드 **1개를 전 세션이 공유**하는 구조이고 동시 접속 부하를 측정한 기록이 없다. 통신은 평문이며 클라이언트가 보내는 인증 키를 서버가 검증하지 않는다 — **현재 구성으로는 사내 배치도 불가**하다.
- **클라우드**는 브라우저의 언어팩 상태에 따라 **12회 연속 측정에서 한국어 인식이 전면 실패한 이력**이 있다. 원인은 제거했지만 팩이 내려오는 것 자체는 우리 코드가 통제하지 못한다. 그리고 오디오가 외부 서비스로 나간다 — 상담 음성은 개인정보다.

### 이 판정의 정밀도

평가 표본은 정답 전사 기준 **총 309자**(짧은 발화 6개 = 142자, 긴 오디오 1개 = 167자)다. 이 규모에서 오류율의 95% 구간은 약 **±5~8%p**다. 따라서 **절대값을 소수점까지 비교하거나 "몇 배" 같은 배수 표현을 쓸 수 없다.** 반면 **순위는 6개 발화 전부에서 동일**하므로(§4.3) 순위에 기반한 위 판정은 이 표본으로 지지된다.

## 2. 권고

### 2-A. 용도별 권고 합격 기준 (기준선이 정해져 있지 않으므로 실측에서 유도한 값)

세 가지 조건을 동시에 본다. 평균 하나로 정하면 **"평균은 좋은데 읽히지 않는" 실패**(SenseVoice형)와 **"평균은 중간인데 특정 발화가 통째로 무너지는" 실패**(Whisper형)를 둘 다 놓친다.

| 용도 | 권고 기준 | 이 숫자의 근거 |
|---|---|---|
| **실시간 자막** | micro CER ≤ **15%** **AND** 어절 WER ≤ **45%** **AND** 발화 CER≥50% 관측 ≤ **2%** | CER 13.4% / 어절 WER 44.2%(faster-whisper small)가 이 저장소에서 **실시간성을 유지한 채 도달한 유일한 실측 지점**이다. 더 정확한 지점은 medium(11.6%/40.3%)뿐인데 실시간 계수 0.93으로 중간 자막 재전사가 밀린다. 어절 WER 조건이 없으면 CER 10.9%인 SenseVoice가 통과하지만 어절 WER 65.3%로 읽히지 않는다 — 이 조건이 필요한 이유다. 2%는 관측 36~48건 규모에서 판별 가능한 최소 단위다(0%를 요구하면 0%와 2%를 구별할 수 없다) |
| **사후 기록·검색** | micro CER ≤ **25%** **AND** 발화 CER≥50% 관측 ≤ **10%** | 25%는 **클라이언트 로컬 배치 경로의 실측(23.4%/24.6%)을 통과시키는 최소 임계**다. 더 낮추면 로컬 단독 사후 기록이 배제되는데 그 배제를 정당화할 실측이 없다. 10%는 온프레미스 실측(0~4%)과 브라우저 로컬 실측(22~28%) 사이에서 온프레미스 쪽 상단을 취한 값이다 |
| **키워드 추출·색인** | **제시 불가** | 키워드 단위 재현율·정밀도 측정이 **0건**이다. 오류가 특정 발화에 뭉치는 분포이므로(§4.3) 평균 CER로 환산할 근거도 없다 — 키워드가 무너진 발화에 있으면 평균이 아무리 좋아도 그 키워드의 재현율은 0%다. 선결 측정 항목으로 제안한다(§2-C ④) |

**"사람이 후처리 없이 읽을 수 있는 최소 CER"은 제시하지 않는다.** 사람 판독 평가 기록이 없고, 한국어 띄어쓰기 교정기(kiwipiepy)를 붙이는 실험은 어절 WER을 65.3% → 74.3%로 **악화**시켰다 — 후처리로 가독성을 회복하는 경로는 막혀 있다.

기준을 적용할 때: **측정 구간이 임계를 걸치면 합격/불합격이 아니라 "판정 보류 + 표본 확대"로 처리한다**(현재 정밀도 ±5~8%p).

### 2-B. 실행 위치 권고 — 조건표

"클라이언트 로컬 권장"이라는 방침과 측정 결과가 충돌하는 지점을 칸 안에 명시한다.

| 조건 | 1순위 | 폴백 | 이 조합의 미해결 제약 |
|---|---|---|---|
| 실시간 자막이 필요하고 **오디오 외부 전송 불가** | 온프레미스 SenseVoice(10.5%) 또는 faster-whisper small(15.8%) | 없음 — 로컬 단독은 기준 미달 | 온프레미스가 **동시 접속 미측정 · 평문 · 인증 미검증**. 이 3건을 해결하지 않으면 1순위가 성립하지 않는다 |
| 실시간 자막이 필요하고 **외부 전송 허용** | 클라우드 WebSpeech(7.5%) | 온프레미스 | Chromium 데스크톱 전용. 언어팩 상태 의존 전면 실패 이력. 마이크 경로는 **자동 검증 불가**(사람 확인 필요) |
| **사후 기록·검색**이 목적 | **클라이언트 로컬 배치**(23.4%) | 온프레미스 | 서버 0대·오디오 미전송으로 방침에 부합. 최초 자산 약 96MB 전송, 로드 시간·메모리 미측정 |
| **서버를 둘 수 없다**는 제약이 절대적 | 클라이언트 로컬 Whisper base | 없음 | 실시간 자막 용도로는 기준 미달(26.5~34.2%, 발화 22~28%가 반파). 용도를 사후 기록으로 재정의해야 성립한다 |
| 세 경로를 한 페이지에서 제공 | — | — | **정책 충돌**: 멀티스레드 WASM에 필요한 COOP/COEP 헤더가 Chrome 인식 서비스를 즉시 깨뜨린다(§7). "고르기" 문제가 아니라 헤더 전략이 상호 배타다 |

> 방침이 "클라이언트 로컬 권장"이라면, 이 표가 제안하는 것은 방침 폐기가 아니라 **용도 재정의**다: 실시간 자막을 요구 사항에서 내리고 사후 기록·색인으로 범위를 좁히면 로컬 단독이 성립한다. 실시간 자막이 필수라면 방침과 측정이 충돌하며, 그 충돌은 온프레미스 3건(동시 접속·암호화·인증)을 해결해야 풀린다.

### 2-C. 선결 측정 4건 — 이 값이 나오기 전에는 위 판정이 확정되지 않는다

| # | 항목 | 지금 근거 | 어느 판정을 바꿀 수 있나 |
|---|---|---|---|
| ① | **물리 마이크 실기 확인** | 없음. QA의 마이크 모드는 파일 재생을 주입한 가짜 마이크다 | 마이크 경로 전체. 특히 클라우드 마이크 경로는 자동 검증이 원리적으로 불가하다(§5) |
| ② | **온프레미스 동시 접속 부하** | 없음. 추론 스레드 1개를 전 세션이 공유한다 | §2-B의 1순위 권고 전체. 실시간 계수 0.36 기준 동시 3명이 이론상 한계지만 실측이 없다 |
| ③ | **브라우저 최초 로드 시간·메모리** | 없음. 전송량 약 96MB만 확인 | 클라이언트 로컬의 실사용 가능성. 저사양 PC·모바일에서의 성립 여부 |
| ④ | **표본 확대 + 키워드 재현율** | 정답 309자, ±5~8%p | 임계 판정의 정밀도. ±2%p로 좁히려면 정답 약 2,150자(발화 80~100개, 오디오 6~8분)가 필요하다. 현재 표본 선정으로는 미사용분을 더해도 ±5.7%p까지만 좁혀진다 → **표본 재선정이 선결 조건** |

### 2-D. 품질 게이트 보강 3건

현재 게이트(`npm run qa:stt` + push 훅)는 회귀 차단에 실효가 있지만 세 곳이 비어 있다.

1. **어절 WER을 게이트 지표에 추가.** CER은 공백을 무시하므로 띄어쓰기 붕괴가 잡히지 않는다 — SenseVoice가 CER 10.9%로 통과하면서 어절 WER 65.3%인 상태가 그 예다.
2. **micro CER 병기.** 현재 판정은 샘플 단순평균(macro)이라 긴 오디오의 가중이 1/7로 축소된다. 실제로 macro/micro가 순위를 뒤집는 사례가 있다(§3.2).
3. **감시 경로 확장.** 게이트가 재측정을 요구하는 경로에 `server/vendor/`(반입한 외부 엔진), `scripts/qa/lib/`(측정 규칙 자체), `src/app.ts`, `src/ui/`가 빠져 있다. 측정 규칙을 고쳐도 게이트가 재측정을 강제하지 않는다.

## 3. 측정 조건과 지표의 한계 — 위 수치를 어디까지 믿을 수 있는가

### 3.1 평가 표본

| 발화 | 길이 | 정답(정규화 후) |
|---|---|---|
| S1 | 3.34초 | 19자 |
| S2 | 2.64초 | 19자 |
| S3 | 2.65초 | 18자 |
| S4 | 6.51초 | 36자 |
| S5 | 5.38초 | 33자 |
| S6 | 2.91초 | 17자 |

짧은 발화 6개 합계 **142자**, 전체 **309자**. 전부 8kHz 전화 음성이다. 마이크 모드는 짧은 발화 6개만 측정한다(긴 오디오 제외).

### 3.2 지표가 재지 못하는 것

| 지표 | 무엇을 재는가 | **재지 못하는 것** |
|---|---|---|
| CER (문자 오류율) | 정답과 인식 결과의 문자 편집거리 ÷ 정답 길이 | **공백·문장부호를 제거한 뒤 계산한다 → 띄어쓰기 품질이 반영되지 않는다.** 100%를 넘을 수 있다(환각으로 정답보다 긴 출력을 낼 때) |
| macro 평균 | 발화별 CER의 단순평균 | 발화 길이 가중을 반영하지 않는다. 최신 실행에서 SenseVoice는 macro 14.1% ↔ micro 23.6%로, **긴 오디오를 포함하면 순위가 뒤집힌다**(macro로는 faster-whisper를 이기고 micro로는 진다) |
| 채택 규칙 | 개별 확정 결과와 전체 이어붙인 결과 중 **CER이 가장 낮은 것**을 채택 | 사용자는 그 선택을 할 수 없다 → **측정값은 화면에 보이는 문장의 오류율보다 낙관적이다** |
| 소요 시간(결과지의 `msAvg`) | 샘플 시작부터 유예 종료까지의 벽시계 시간 | **오디오 재생 시간과 고정 유예 1.5초를 포함한다 → 지연 지표로 직접 쓸 수 없다.** 이 문서는 `소요 − 재생 − 1.5초`로 역산한 **확정 잔여(tail)** 를 쓴다 |
| 중간 결과 카운터 | — | **자막 갱신 빈도를 판정할 수 없다**(중간 자막을 끈 구성에서도 1로 기록된다). 중간 자막의 정확도·갱신 빈도는 미측정 |

### 3.3 "HEAD 구성"의 정의

결과지에는 코드가 바뀌는 도중의 실행이 함께 쌓여 있다. 판정에는 **현재 코드(HEAD)와 같은 조건**만 사용했다 — 구체적으로 ① 클라우드 전면 실패를 유발한 환경 요인을 제거한 뒤, ② 온프레미스 기본 엔진을 faster-whisper small로 교체한 뒤의 실행이다. 기능당 6~8회 측정, 발화 관측 36~48건이다.

§1·§2·§4의 표는 이 범위이고, 유실 전수 집계(§4.6)와 재현성(§4.7)만 전 기간을 함께 본다.

### 3.4 이 판정을 뒤집을 수 있는 조건

- 서비스 오디오가 8kHz 전화 음성이 아니라면 **모든 수치를 다시 재야 한다**(16kHz 미측정).
- 표본이 309자이므로 ±5~8%p 안의 차이는 판별할 수 없다. **온프레미스 faster-whisper(16.9%)와 SenseVoice(10.9%)의 우열은 이 표본으로 확정되지 않는다** — 어절 WER을 함께 보면 방향이 갈린다(§4.4).
- 클라이언트 로컬과 나머지의 격차(26.5~34.2% vs 7.5~16.9%)는 ±8%p를 넘으므로 이 표본으로도 유효하다.

SenseVoice는 CER이 준수한데 어절 WER이 65%다 — 문장부호를 거의 넣지 않고 간헐적으로 음절을 분리한다. 띄어쓰기 교정기 후처리는 오인식 단어를 더 쪼개 WER을 74.3%로 **악화**시켰다. **띄어쓰기는 후처리 문제가 아니라 인식 정확도 문제**이고, 해결은 엔진 교체였다(기본 엔진을 small로 바꾼 뒤 QA CER이 파일 28.4%→14.5%, 마이크 23.7%→10.4%로 내려갔다).

### 4.5 클라이언트 로컬 모델 선택 — 정확도와 실시간성의 교환

| 구성 | 짧은 발화 CER(micro) | 긴 오디오(L1) CER | 확정 잔여(중앙) | 실시간 추종 | 모델 자산 |
|---|---|---|---|---|---|
| whisper tiny | 49.3% | 47.9% | 1,820ms | 가능 | 39MB |
| **whisper base (현재 기본)** | **33.8%** | **18.3%** | **1,263~1,520ms** | **가능** (35초 오디오에서 잔여 1.9초) | 73MB |
| whisper small | 17.6% | 23.4% | **13,294ms** | **불가** | 238MB |
| whisper base · 배치(전체 일괄 인식) | 24.6% | **23.4%** | 실시간 아님 | 해당 없음 | 73MB |

- **small은 정확도를 얻고 실시간성을 잃는다.** 2.6초짜리 발화도 확정이 **13초 뒤**에 오고(입력을 30초 창으로 패딩하므로 발화 길이와 무관하게 13~15초 고정), 35.09초 연속 오디오는 오디오가 끝난 뒤에도 **47.7초를 더 기다려야** 마지막 확정이 온다(전체 처리 84.3초 = 오디오 길이의 2.4배). 같은 파일에서 base는 잔여 1.9초로 실시간을 따라간다.
- tiny는 8kHz 전화 음성에서 사실상 사용 불가다. 고정 5초 청크로 자르던 시절에는 발화 중간이 끊겨 **CER 458%**(정답보다 몇 배 긴 반복 환각)까지 나왔다.
- **배치 경로가 실시간을 포기한 대가로 CER 23.4%를 준다** — 사후 기록 용도의 근거가 이것이다.

### 4.6 확정 유실 — 안정성 순위는 정확도 순위와 반대다

`확정 결과가 한 건도 오지 않은 발화` 전수 집계(전 기간):

| 실행 위치 | 측정 | 발화 관측 | 유실 | 내역 |
|---|---|---|---|---|
| **클라이언트 로컬(Whisper 계열)** | 94 | 597 | **0건** | — |
| 온프레미스 | 144 | 975 | 25건 | 실험 엔진(whisper_streaming) 18 · faster-whisper 5 · FunASR 2 |
| 클라우드 | 60 | 354 | 206건 | 마이크 경로 126 · 파일 경로 68 · 온디바이스 12 |

> "측정"은 기능 단위 실행 횟수다(순회 1회가 기능 12개를 측정한다).

성격이 다르므로 뭉쳐 읽으면 안 된다.

- **클라우드 파일 경로 68건은 전부 특정 구간(2026-07-29)의 환경 요인**이다 — 한국어 온디바이스 언어팩이 특정 상태로 보고되면 온라인 경로까지 전부 즉시 실패한다. 원인을 제거한 뒤 **HEAD 구성 6회 측정에서 유실 0 · CER 5.0~8.7%로 결정론적**이다.
- **클라우드 마이크 126건은 "무응답"**이다(확정 0건 + 중간 결과 0건). 오인식이 아니고, **이 측정이 마이크 경로를 대변하지 못하는 항목**이다(§5).
- **온프레미스 faster-whisper 5건**은 원인 3종이다: 강제 확정 길이가 모델 속도보다 길어 확정이 클라이언트 종료 뒤 도착 / 전사가 코어를 점유해 서버가 정상 연결을 끊음(keepalive) / 두 엔진 동시 기동으로 CPU 경합. 앞의 둘은 수정했고, **마지막 유실 이후 파일 경로 7회·마이크 경로 4회 무유실**이다. 다만 수정 이후 측정 횟수가 적다.
- **클라이언트 로컬은 597건 관측에서 유실 0건**이다. 이 경로의 문제는 "결과가 안 오는 것"이 아니라 "온 결과가 틀리는 것"이다.

| 기능 | HEAD 구성 측정 | CER 범위 | 폭 |
|---|---|---|---|
| 클라우드 WebSpeech(파일) | 6 | 5.0~8.7% | 3.7%p |
| 온프렘 SenseVoice(마이크) | 6 | 9.5~11.7% | 2.3%p |
| 온프렘 SenseVoice(파일) | 6 | 14.0~16.7% | 2.7%p |
| 로컬 Whisper base(마이크) | 6 | 23.6~27.8% | 4.1%p |
| 로컬 Whisper base(파일) | 6 | 27.9~37.2% | **9.4%p** |
| 온프렘 faster-whisper(파일) | 8 | 15.3~27.6% | **12.3%p** |

- 게이트 허용오차는 5%p(클라우드 7%p)인데 **관측 폭이 그보다 큰 기능이 셋**이다. 게이트가 실제로 잡는 것은 "회귀"라기보다 **"관측 폭을 넘는 큰 변화"**이고, 그 이하는 판별하지 못한다.

- 로컬 파일 경로의 9.4%p는 무음 경계 분할이 시스템 부하에 따라 조각 수를 바꾸기 때문이다.

### 4.8 긴 연속 오디오(L1, 35.09초·167자) — 짧은 발화의 순위가 유지되지 않는다

| 온프렘 SenseVoice(파일) | 6 | **35.3%** | 32.3~40.7% | 2~3 |
| 온프렘 FunASR(파일) | 6 | 96.1% | 95.8~97.0% | 1 |

- **짧은 발화 강자였던 SenseVoice가 긴 오디오에서 무너진다**(10.9% → 35.3%). 반대로 **로컬 Whisper base는 긴 오디오에서 18.3%로, 짧은 발화(34.2%)보다 훨씬 좋다** — 무음 경계로 발화를 잘라 확정하는 구조가 연속 오디오에 유리하게 작동한다.
- 이것이 §3.2에서 macro/micro가 순위를 뒤집는 이유다. 긴 오디오가 정답 문자 수의 54%를 차지하기 때문이다.
- faster-whisper의 100% 1건은 앞서 언급한 확정 유실이다.

### 4.9 한국어 실시간 STT에서 선택지가 좁은 이유 (조사·실측 결과)

| 후보 | 결과 | 판단 |
|---|---|---|
| 한국어 증분 스트리밍 모델 A(zipformer 계열, 진짜 online) | CER 72.8% · 어절 WER 100% — **공백을 아예 출력하지 않는다** | 8kHz 상담 음성에서 붕괴. 사용 불가 |

## 부록 C. 품질 게이트의 현재 상태와 사각지대

**있는 것**: 12개 실행 경로 자동 순회 → 기능별 결과지 → 기준선 대비 판정 → push 훅이 결과지 검사(판정 통과 + 결과지가 지금 소스로 측정된 것인지 해시 확인 + 평가 표본 정답·정규화 규칙 동일성 확인). STT 소스가 바뀌지 않은 푸시는 통과시킨다.

**사각지대**:
1. 감시 경로에 `server/vendor/`(반입 엔진), `scripts/qa/lib/`(측정 규칙), `src/app.ts`, `src/ui/`가 없다 → 측정 규칙을 고쳐도 재측정이 강제되지 않는다.
2. 저장된 모든 실행이 "작업 트리 변경 있음" 상태로 기록됐다 → 기록된 커밋이 측정 대상 코드를 완전히 식별하지 않는다.
3. 허용오차(5%p)가 일부 기능의 관측 폭(9.4~31.7%p)보다 작다(§4.7).
4. CER이 공백을 무시하므로 띄어쓰기 회귀가 잡히지 않는다.

## 부록 D. 재현 방법

```bash
npm run qa:samples   # 평가 표본 선정(최초 1회)
npm run qa:stt       # 전 기능 자동 측정 → 결과지 + 판정
npm run qa:gate      # 측정 없이 최신 결과지 재판정
npm run qa:mic -- whisper local-client   # 마이크 경로 보조 검증
```

- 결과지: `stt-e2e/<날짜>/<기능>.json`(같은 날 재실행은 누적), `summary.md`/`summary.json`, 기준선 `stt-e2e/baseline.json`.
- 이 문서의 표는 `runs[].items[]`(발화 단위 `cer`·`distance`·`refLength`·`ms`·확정 건수)에서 재집계했다.
- 확정 잔여(tail) = `ms − 발화길이×1000 − 1500`. 1500ms는 중지 후 결과 수집 유예다.
- 표본 확대: `npm run qa:stt -- --samples 8` (기준선은 표본이 바뀌면 다시 세워야 한다).

## 부록 E. 지표 정의

- **CER(문자 오류율)**: 정답과 인식 결과를 소문자화하고 한글·영문·숫자만 남긴 뒤 편집거리 ÷ 정답 길이. **공백·문장부호는 제거된다.** 100%를 넘을 수 있다.
- **micro CER**: 전체 오류 문자 수 ÷ 전체 정답 문자 수. 긴 발화가 길이만큼 가중된다.
- **macro CER**: 발화별 CER의 단순평균. 결과지의 `cerAvg`가 이것이다.
- **어절 WER**: 공백 단위 단어 오류율. 띄어쓰기·문장부호 품질을 반영한다. 이 저장소의 상시 측정 항목이 아니라 별도 실측값이다.
- **확정 잔여(tail)**: 오디오가 끝난 뒤 확정 결과가 도착할 때까지의 시간(역산값).
- **실시간 계수**: 오디오 1초를 처리하는 데 걸리는 시간. 1.0을 넘으면 실시간을 따라가지 못한다.
- **확정 유실**: 한 발화에서 확정 결과가 한 건도 오지 않은 경우.
